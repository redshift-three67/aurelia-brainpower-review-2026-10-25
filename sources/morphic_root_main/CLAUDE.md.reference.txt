## 🔄 MIGRATIONSABLAUF-PATTERN (weiterhin gültig für CLI-Refactoring-artige Arbeit)

1. **Find:** `grep -n "^def function_name" apps/cli/main.py`
2. **Import:** Abhängigkeiten prüfen (`grep function_name main.py -B 50 | grep "^import\|^from"`)
3. **Copy:** Vollständig nach `commands/*.py` inkl. Helper-Funktionen und Constants
4. **Test:** `python -m apps.cli.main COMMAND --help`
5. **Remove:** Erst nach erfolgreichem Test aus `main.py` löschen
6. **Commit:** `git commit -m "migrate: FUNCTION_NAME from main.py to COMMAND.py"`

## � TDD-PATTERN (für die aktuelle UI/UX-Konsolidierung, siehe Plan-Doc)

1. Test zuerst schreiben (Backend-Änderungen), Fehlschlag bestätigen
2. Implementieren, Test grün bekommen
3. Für reine Frontend-Änderungen (HTML/CSS/JS ohne Backend-Contract): manuelle Verifikation gemäß
   Verifikationsplan im Plan-Dokument (Abschnitt 4), da JS aktuell ohne Test-Runner läuft
4. Nach jedem Task: volle Suite (`pytest tests -q`) + `node --check` auf geänderten JS-Dateien
5. Commit mit klarer Task-Referenz (siehe Commit `3a957a3` als Vorlage für WIP-Commit-Stil)

- Aktiver Branch für Code-Änderungen: `operator-workbench-phase1` (im Worktree), **nicht** `master`

### ⚠️ ENCODING:
- Windows CP1252 kann UTF-8 nicht lesen → `PYTHONIOENCODING=utf-8`, `PYTHONUTF8=1` setzen
- Keine `\u2011` (non-breaking hyphen) in Docstrings/Strings

  Frontend muss `Object.values()` verwenden (bereits gefixt in `workbench-render.js`, aber bei
  neuen Konsumenten dieses Payloads beachten)
