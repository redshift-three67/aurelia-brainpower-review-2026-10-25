# RadiWorks: isolierter Browser-Smoke (Entwicklung)

Dieser Test startet eine **eigene** RadiWorks-Engine auf einem freien `127.0.0.1`-Port, erzeugt nur künstliche Raten in einem neuen temporären Runtime-Home und öffnet einen sichtbaren Chrome-Browser mit 390-px-Ansicht. Er berührt weder die vorhandenen Instanzen auf 8090/8101 noch reale Kataloge. Browser, Engine und Test-Home werden am Ende geschlossen bzw. entfernt.

Voraussetzungen: Python-Engine im Verzeichnis `radiworks_port/engine` mit `.venv` und `pip install -e ".[dev]"`; Node.js, npm und Chrome. Nur für diesen Entwicklungstest wird Playwright benötigt; es ist keine Produktionsabhängigkeit der Engine.

```powershell
cd radiworks_port\engine\tools\browser_smoke
npm ci
npm run smoke
```

Optional: `RW_SMOKE_PYTHON` setzt den Engine-Python-Pfad, `RW_SMOKE_TMP_ROOT` ein vorhandenes beschreibbares Testverzeichnis und `RW_SMOKE_BROWSER=chromium` nutzt einen separat installierten Playwright-Chromium statt Chrome. `RW_SMOKE_CONTRAST_ONLY=1` führt nur den neuen Header-Kontrastabschnitt aus und bereinigt Browser und Test-Home regulär; das ist **kein** vollständiger Browser-Smoke. Der Test verlangt einen sichtbaren Desktop. Alle Requests des Testbrowsers außer denen an seinen eigens gestarteten Loopback-Port werden abgebrochen.

`package-lock.json` pinnt nur die Entwicklungsabhängigkeiten dieses Browser-Tests. `npm ci` installiert sie lokal im Testordner. Für eine frische Python-Umgebung zuvor im Engine-Verzeichnis `python -m venv .venv` und mit deren Python `-m pip install -e ".[dev]"` ausführen; die Python-Abhängigkeiten sind in `pyproject.toml` derzeit nur mit Mindestversionen versehen, also nicht vollständig versionsfixiert.

Geprüft werden Engine/Webapp/WebSocket, ein zulässiger Seed-Analyse→Ready→Promote→virtuelle Queue→Stop-Ablauf und ein künstlicher CopyGuard-Block vor der Queue. Zusätzlich muss der blockierte Ratenname in Browser und aktuellem Analyse-API fehlen; sein Direktknopf muss gesperrt sein. Beide Fall-Editoren werden mit einem synthetischen aktiven Fall durchlaufen: Ein gesperrter Beschreibungstext muss verständlich abgelehnt werden, sichere Metadaten müssen speicherbar bleiben. Lokale Bilddateinamen dürfen in Dateifeldern, Tabelle und Area-Status nicht erscheinen. Die Stick-Pad-Ergebnistabelle muss eine gesperrte Rate zurückhalten; die virtuelle Queue bleibt leer. Zwei geschützte Fälle müssen über unterschiedliche opake Verweise geladen und nach einem Browser-Reload wieder ausgewählt werden können. Für die Kamera werden ein künstlicher Gerätename und ein Browserfehler simuliert; beide dürfen nicht als Rohtext erscheinen. Ein grüner Test ist allein keine S4- oder Aurelia-Freigabe; Bildinhalt, weitere Textzustände und Hostverträge brauchen eigene Nachweise.

Am 29.09.2026 wurde der aktuelle uncommittete Quellstand in einen neuen Testordner ohne `.venv` und `node_modules` kopiert. Dort bestanden `npm ci --offline`, eine neue Python-3.13-Umgebung mit `pip install -e ".[dev]"` und der sichtbare Chrome-Smoke 8/8. Das ist ein frischer **Quellexport mit Neuinstallation**, kein Git-Checkout eines versionierten Commits und kein Nachweis für Debian.

Die beiden später hinzugefügten Abschnitte für Fallverweise und Kamera liefen am selben Tag im isolierten lokalen Browser-Smoke grün (10/10). Die opaken Fallverweise gelten nur bis zum Neustart der Engine; danach kann der Fall aus der frisch geladenen Liste erneut gewählt werden. Die persistierte Falldatei bleibt unverändert. Dies wurde noch nicht als Clean-Checkout- oder Debian-Probe wiederholt.

S4.6-Zustandsfortsetzung: Vier weitere Abschnitte prüfen die ARIA-Zuordnung der Tabs und Pfeil-/Home-/End-Navigation, eine wirklich leere Fallliste, Offline-Anzeige und automatisches WebSocket-Reconnect nach gezieltem Schließen der Testverbindung sowie einen abgebrochenen Falllisten-/Ladevorgang mit sichtbarer Fehlermeldung und Retry. Der isolierte Chrome-Lauf bestand 14/14 Abschnitte. Das prüft ausgewählte Zustände, keine vollständige WCAG-2.2-AA-Konformität oder alle Netzwerk-/Fehlerkombinationen.

S4.6-Kontrastfortsetzung 29.09.2026: Ein zusätzlicher Abschnitt misst im isolierten Browser die effektive Schrift-/Hintergrund-Kontrastzahl für Werkbank-Untertitel, Akzentlabel und Fall-Badge in allen sechs Kombinationen aus Hell/Dunkel und drei Akzenten (mindestens 4,5:1). Er prüft nach Tastaturfokus außerdem die Fokusrahmen von Modusschalter und Akzentauswahl gegen den Header-Hintergrund (mindestens 3:1). Vor den CSS-Korrekturen lagen sechs Text- und alle sechs Modusschalter-Fokuswerte unter diesen Grenzen; danach bestand der gezielte Abschnitt für beide Header-Bedienelemente. Der Fall-Badge hat weniger transparente Aufhellung und keine Gesamt-Opacity, der dunkle Wellenreiter-Akzent wird aus dem Modulblau und heller Basistinte gemischt, und die Header-Bedienelemente nutzen den Kontrast-Token als Fokusfarbe. Dies ist eine begrenzte Header-Probe, keine vollständige WCAG- oder Screenreader-Abnahme. Ein erster vollständiger Lauf endete bei weniger als 1 GB freiem virtuellem Windows-Speicher vor der letzten Fehler-/Retry-Probe; sein verwaistes rein synthetisches Home wurde entfernt. Mit ausreichender Speicherreserve bestand der vollständige 17/17-Lauf auf dem bytegleichen Test-Checkout. Nach Korrektur einer kollidierenden CopyGuard-Schlüsselprojektion bestanden der Arbeitsstand und ein neuer bytegleicher Checkout erneut 17/17 Abschnitte mit regulärem Cleanup. Das bleibt ein lokaler Windows-Entwicklungsnachweis, kein kanonischer Release oder vollständiger WCAG-/Screenreader-Nachweis.
