## Trust and architecture

This is a loopback-only, single-operator Python application. It is an additive control plane; existing product repositories, migrations, deployments and gate decisions are not implementation scope. The browser never supplies an executable shell command. Model output is data, never a command or an approval.

`config.py` resolves portable paths and validates known project IDs, a cycle-free dependency graph, permitted model roles and the local router. `evidence.py` reads bounded Markdown sources and tracked Git state, hashes changed files, distinguishes HEAD/index/current contents, and performs conflict-checked existing-memory writes. `store.py` owns a separate SQLite WAL journal. `jobs.py` owns one worker and allowlisted actions. `server.py` owns observation, local HTTP/session/CSRF checks and SSE. `__main__.py` owns initialization, diagnosis, exports and exclusive instance locking.

`llm.py` handles bounded Responses requests and strict model/structured-result validation. `hermes.py` and `hermes_runner.py` execute the Terra side using the existing Hermes Python environment, an isolated temporary home and zero active tools. Sol or Astra receives an independent supervisor request through CC Switch. `orchestrator_transport=router` is an explicit alternative, never a hidden fallback. See `MODEL_INTEGRATION.md` for the validated transport differences.

The UI uses vanilla JS/CSS and safe text nodes for source/model content. There is no production frontend build chain or package download. Local documented sources and existing scripts are not treated as executable instructions.

## State and freshness

Project `gate`, configured `status` and `next_step` are visibly labeled as an operator planning baseline. They are not silently upgraded by tests or models. Actual goals/snapshot statuses are parsed and their different statements displayed. A lexical difference is evidence of different source statements, not proof of semantic incompatibility or a new gate decision.

`evidence_hash` covers review-relevant project metadata, current source hashes, HEAD, changed tracked content, known memory state, warnings and planned modules. Source observation is every 15 seconds; cached Git facts are refreshed every 60 seconds, and explicit reviews/tests force Git refresh. SHA-256 comparison binds reviews to their input state. A later mismatch makes the historical result stale without rewriting its original outcome.

Current Markdown bytes are compared with HEAD/index content. The model distinguishes `tracked_in_head`, `has_staged_changes`, `committed` and `staged`; the last two refer to the current byte content. Git line-ending normalization can therefore mean a clean tracked Markdown file does not have byte-identical HEAD content. This is presented as a strict byte-evidence distinction, not as a claim that the repository is corrupt.

Changed tracked hashing is bounded to 64 MiB and 1,000 paths per scan; memory enumeration is bounded to 100 files per project and 512 KiB each. Exceeding bounds or failed required observations marks evidence incomplete. Indeterminate evidence cannot establish fresh approval and does not trigger automatic paid reviews. Large untracked product trees are not recursively scanned; this scope limit is visible.

Browser/scope context contains bounded first/last excerpts of each selected memory plus governance documents, IDs, Git/gate facts and applicable test results. For explicitly started legacy-hybrid and Route-B review/plan jobs, `model_memory.complete_memories` reloads every selected project memory and checks inventory and SHA-256. When the full context exceeds the review cap, `stage_memories` reads every source chunk independently through the selected route's lead and reviewer models (and Astra for legacy comparison), validates exact quotations, records contiguous character coverage and rechecks source hashes before each call. A versioned local digest cache is keyed by project, file SHA, chunk SHA, model and effective reasoning. The final prompt gets bounded digests, exact quotations and the original heading index; `memory_coverage.status=staged` explicitly distinguishes this from a full-raw final prompt. Missing coverage, invalid quotes, source drift or a still-oversized final prompt fail closed. The job stores a coverage manifest and hash of the actual final model context. Strategy adoption checks staged coverage before accepting a clean plan result. The 95,000-character review-context and per-transport limits remain unchanged; there is no silent fallback to browser excerpts. Vault sources and untracked product trees retain separately marked limits. Staging adds initial model calls and cannot prove a model noticed every fact; cached tokens and reasoning tokens are recorded only when provided by the upstream API. See [memory verification](verification/HERMES_MEMORY_2026-09-25.md) and [staged-memory release review](verification/HERMES_MEMORY_STAGES_2026-09-26.md).

## Persistence and action lifecycle

SQLite tables: `jobs`, `events`, `settings`, `planned`. Only the Workbench owns this database. Opening the application journal during startup marks unfinished jobs interrupted; consequently external diagnostic code must use SQLite read-only access rather than constructing a second `Store` against a live journal.

`queued → running → completed / failed / cancelled`. On process restart unfinished jobs become `interrupted`. One queued or active job at a time prevents double execution and resource contention. Stop/cancel targets only the owned child. There is no automatic replay of writes or model requests. Events are retained up to approximately 10,000 records; job details and backups remain in the runtime directory and require operator-managed archival as they accumulate.

RadiWorks tests use its own existing interpreter, an isolated runtime home and unique temporary directory, no bytecode/cache writes in the source tree, and a JUnit result. A successful test action does not authorize integration. Comparison of before/after source evidence is recorded separately from the test return code.

The monitor persists an automatic-review baseline, last attempt and daily counter. Automatic review is opt-in, min. 900 seconds between attempts and max. four per UTC-day by default. Failed attempts count. It only schedules a review after a determinable source change. It does not modify products. In this delivered state automatic review is disabled pending explicit authorization for transmission of real source excerpts.

## HTTP API

Bind `127.0.0.1` only. Allowed Host values include the actual configured port and either 127.0.0.1 or localhost. Cross-site fetches are rejected; mutating calls additionally require an HttpOnly SameSite=Strict cookie, exact Origin and `X-CSRF-Token`. No CORS wildcard. Responses use no-store, nosniff and restrictive CSP. This is local user-session isolation, not a multi-tenant internet deployment design.

| Route | Contract |
|---|---|
| `GET /health` | Service identity/version; no model inference. |
| `GET /api/state` | Session bootstrap, CSRF token, current observations, jobs, events, settings and planned modules. Do not publish this response unredacted as an artifact. |
| `GET /api/events` | SSE `state` events and heartbeat; bounded to eight concurrent streams and a 90-second reconnect cycle. |
| `GET /api/memory?project=ID&name=NAME.md` | Existing validated memory text and SHA-256. |
| `POST /api/memory` | `project`, `name`, `content`, `expected_sha256`; conflict409, backup + atomic replacement + readback on success. |
| `POST /api/actions` | `action`, optional `project_id`/`supervisor`; creates job202; busy409. |
| `POST /api/jobs/cancel` | `id`; cancel active owned job. |
| `POST /api/settings` | `supervisor`, `monitor_enabled`, `auto_review`; strict allowed fields/types. |
| `POST /api/projects` | `name` <=80, `description` <=4000, `depends_on`; creates planned entry201, no repository. |
| `POST /api/shutdown` | Graceful local stop. |

Allowed actions: `refresh`, `hybrid_review`, `model_check`, `radiworks_tests`, `hermes_check`. `hermes_check` includes an isolated zero-network, zero-tool capability probe when the installation is present. Model errors do not include raw response bodies or credentials. The live UI distinguishes router reachability from actual inference success and stale results from historical completion.

## Credentials and Hermes compatibility

Configuration stores paths and environment-variable names, never tokens. The direct adapter can read a configured environment variable or the explicitly configured existing Codex access token. Codex credentials are limited to the intended loopback CC Switch endpoint, and redirects are refused. The application does not refresh/redeem credentials or switch accounts.

Hermes is tested at21.1. Its isolated process imports the installed Python API, not a guessed checkout; suppresses repo dotenv loading/custom context; uses no tools, no MCP servers and no fallback; asserts the actual resolved tool list; validates the request model/reasoning/store flag; and refuses unexpected tool dispatch. Python audit checks additionally block child processes, writes outside its temporary home and connections outside loopback3000. These are defense-in-depth for trusted installed Hermes code, not a claim of OS sandboxing against malicious native code. Compatibility relies on verified API/internal seams and needs revalidation after Hermes updates.

## Bounded explicit standalone test attempts

Each `(candidate_id, step_id)` admits at most three journaled `plan_test` jobs. All statuses count; reselection does not reset the budget. Admission under the runner lock rejects active duplicates and exhausted budgets before inserting a job. The worker separately requires the newest active attempt within the cap before staging. Source/selection/predecessor checks still run before and after successful execution. A successful third receipt remains usable, subject to normal freshness checks. The chain response exposes `test_attempts` (used, limit, remaining, reason, last three jobs); the UI displays budget/history and removes the start action when blocked. A new explicit plan is required for another budget. This is a bounded manual retry facility, not automatic repair or follow-up execution. ## S1a: local sequence preview only

Protected `POST /api/sequences/preview` accepts exactly `{stage_job_id}` and returns a diagnostic for `pilot_test_assess_v1` (proposed `stage_test` then `pilot_assess`). ## S1b: internal sequence journal and reservation

`sequence_store.SequenceJournal` is persistence only: it does not dispatch a worker, expose HTTP admission or execute files/models. Its binding hash verifies stored identity, not authorization. The S1c controller reconstructs the current preview and explicit consent before admission, checks source/files/policy/routing/adapter before dispatch and model egress, and verifies evidence again before transition. `finish_child(..., evidence_current=False)` blocks by default; passing true is a controller responsibility, not a file check performed by the journal.

Additive SQLite tables preserve existing jobs. `BEGIN IMMEDIATE` covers reservation plus first child, child outcome plus next child, and cancellation. Unique constraints allow one active reservation globally, one run per staged patch job and at most two fixed children (`stage_test`, then `pilot_assess`). Identical binding/hash/note retries return the same historical run; conflicting retries fail, including after interruption. Consent, child links and events cannot be rewritten; terminal sequences cannot be updated/deleted. This protects application history, not against an administrator replacing the database.

Ordinary job creation and operator-question resume share `require_idle`; automatic reviews and existing manual submissions inherit it. Running cancellation records intent and retains the reservation until the child finishes; no follow-up is allocated. Cancelling a queued child terminates it immediately. Startup interrupts unfinished jobs and active sequences in one transaction without requeueing. Instantiate `Store` only for application startup, not for inspecting a running service: initialization deliberately performs recovery.

Storage tests use isolated SQLite databases and independent connections for competing starts and cancellation/transition races, injected insert failures for rollback, restart at either child, legacy schema migration and existing admission paths. Worker/controller integration is tested separately below; real model quality, live product execution and server deployment remain outside these tests.

## S1c: explicit bounded pilot sequence

Protected POST `/api/sequences/start` accepts exactly `{stage_job_id,binding_hash,note}`; note is nonempty and at most 2000 characters. Under the runner lock, a new start reconstructs the preview, compares its hash and atomically reserves its first ordinary job. An identical retry returns history without requeueing, even after cancellation/interruption; conflicting reuse is rejected. POST `/api/sequences/cancel` accepts exactly `{sequence_id}`. Cancelling a linked child through the existing jobs endpoint cancels its whole sequence, including an already allocated successor.

The existing worker executes the existing `stage_test` and `pilot_assess` adapters. Before each child, before each supervisor transport call and after execution, `validate_child` reconstructs all preview prerequisites and compares the original consent binding. Only the latest-test reference changes to the owned first child. Drift after tests preserves the actual output but marks the result stale and unverified. Failed, incomplete or unverified tests cannot allocate an assessment; a completed assessment without exact `evidence_usable=true` blocks the sequence. Successful completion is terminal `awaiting_transfer_decision`; no prepare/apply/plan-completion action is dispatched. Filesystem checks remain observations, not atomic snapshots or an OS security boundary.

The Jobs panel offers a preview dialog describing model transmission, selected supervisor/Medium, required reason and halt before transfer. Preview, navigation and reload never start execution. Last 40 runs, child references, binding/events, cancellation intent and historical terminal status are returned in `/api/state` and displayed independently of short job history. Existing separate transfer/rollback controls retain their own gates.

Acceptance includes a real temporary HTTP/worker sequence with real unittest execution and simulated supervisor replies, exactly two children, unchanged target bytes before separate transfer, idempotent retry, and the existing separately approved transfer/follow-up/rollback chain. Controller tests cover cancellation, failures, negative assessment and source/selection/routing/egress drift. Browser UI tests use synthetic API responses; they are not real model evaluations or product approvals.

Rejected POST bodies: before replying 403 for failed Host/Origin/session/CSRF checks, the handler discards at most the declared 1 MiB with a 250 ms total deadline, then closes. Content is never parsed or executed. Oversized, malformed-length and transfer-encoded requests are not drained. Partial bodies cannot hold the rejection indefinitely. A regression first demonstrated unread bytes at the previous response boundary; this closes a TCP-reset risk found while investigating a Windows reset in the existing forbidden-origin transfer test. Unit boundary/limit checks, a real partial-body socket test and the original transfer test pass. This is not a guarantee of response delivery for arbitrary incomplete/oversized clients or evidence that all possible network resets are fixed.
